Mimari Kural (application.yml ve compose.yaml Neden Ignore Edilmez?):
Ana application.yml, Dockerfile ve compose.yaml dosyaları projenin ayrılmaz mimari parçalarıdır ve CI/CD pipeline'ında testlerin çalışabilmesi için kesinlikle depoya gönderilmelidir. Yalnızca geliştiricinin kendi makinesine özel ayarları (application-local.yml), yerel şifreleri (.env) ve yerel port çakışmalarını çözen compose.override.yaml dosyası .gitignore ile izole edilir.

2 Kurumsal Dokümantasyon (Lokal README.md & LICENSE)

Kritik Uyarı (Zero Unrelated Histories Garantisi):
GitHub web arayüzünde yeni bir repo açarken "Add a README file" veya "Choose a license" kutucukları işaretlenirse, GitHub remote tarafta bağımsız bir başlangıç commit'i oluşturur. Bu durum, lokaldeki projenizi push ederken meşhur fatal: refusing to merge unrelated histories hatasına ve branch çakışmalarına yol açar.
Kural: README.md ve LICENSE dosyaları her zaman lokalde, ilk commit atılmadan önce oluşturulmalıdır.

3 Lokal Git Başlatma & Çift Dal Mimarisi (`main` & `development`)

Kurumsal mimaride doğrudan main dalına kod yazılmaz. main daima üretime hazır, mühürlü kararlı daldır. Geliştirme akışı development dalında sürdürülür.

Çift Dal (Model B - Enterprise Release Flow) Yaşam Döngüsü:

1. main dalı ilklendirilir ve ilk temiz iskelet commit'i buraya kaydedilir.

2. Hemen ardından aktif geliştirme dalı olan development dalı türetilir.

3. Geliştirici tüm geliştirmelerini development dalında sürdürür ve buraya push eder. Her push/PR anında CI Kalite Kapısı (Quality Gate) tetiklenir.

4. Sprint veya sürüm teslimatında development dalından main dalına Pull Request (PR) açılır. Review ve onayların ardından maine birleştirilir ve sürüm etiketi (Git Release Tag: v1.0.0) basılır.

Terminal (Lokal İlklendirme Komutları)
# 1. Depoyu varsayılan 'main' dalı ile ilklendirin:
git init -b main

# 2. Hazırlanan .gitignore, README.md, LICENSE ve proje kodlarını ekleyin:
git add .

# 3. İlk temiz iskelet commit'ini atın (Conventional Commit):
git commit -m "chore: initial enterprise scaffolding with Spring Boot, Docker and PostgreSQL"

# 4. Geliştirme dalını (development) oluşturup bu dala geçin:
git checkout -b development

# 5. Mevcut durumu teyit edin (development üzerinde olmalısınız):
git status

4 Remote Repo Oluşturma & GitHub Governance Ayarları

GitHub üzerinde remote deponun oluşturulması ve kurumsal yönetişim (governance) güvenlik politikalarının yapılandırılması.

A. Boş Remote Repo Açma (2 Yöntem)

Yöntem Uygulama Komutu / Yönergesi Önemli Güvenlik Kuralı
1. GitHub CLI (Önerilen) gh repo create core-api-service --private --source=. --remote=origin Lokaldeki dosyaları korur, remote'ta bağımsız commit oluşturmaz.
2. GitHub Web Arayüzü github.com > New Repository > Repo Name: core-api-service TÜM KUTUCUKLAR BOŞ KALMALI: README, .gitignore ve License kutucuklarını kesinlikle İŞARETLEMEYİN!
Dalları Remote Depoya İlk Gönderim (Push)
# Remote origin bağlantısını ekleyin (Web arayüzünden açtıysanız):
git remote add origin https://github.com/<ORGANIZATION-OR-USERNAME>/core-api-service.git

# Önce 'main' dalını remote'a gönderin:
git push -u origin main

# Ardından aktif geliştirme dalı olan 'development' dalını gönderin:
git push -u origin development

B. GitHub Repository Settings (Yönetişim Konfigürasyonu)

GitHub üzerinde Settings > General sekmesine gidin ve şu 3 ayarı aktifleştirin:

Ayar Adı Seçim / Durum Gerekçe
Allow auto-merge AKTİF (Checked) CI testleri yeşil yandığında PR'ın otomatik merge olabilmesi için zorunludur.
Automatically delete head branches AKTİF (Checked) Feature branch'ler merge edildikten sonra deponun temiz kalmasını sağlar.
Allow Squash merging AKTİF (Checked) Temiz bir Git geçmişi ve atomic commit takibi için gereklidir.

C. Branch Protection Rules (`main` Dalını Kilitleme)

GitHub'da Settings > Branches > Add branch protection rule seçeneğine tıklayın:

  • Branch name pattern: main
  • ✅ Require a pull request before merging: Doğrudan maine push atılmasını engeller.
  • ✅ Require status checks to pass before merging: CI pipeline'ı yeşil yanmadan merge edilmesini yasaklar. Arama kutusuna build-and-verify yazıp seçin.
  • ✅ Do not allow bypassing the above settings: Yönetici (Admin) kullanıcıların dahi bu kuralı delmesini engeller.

5 Kurumsal CI/CD Kalite Kapısı (Enterprise Quality Gate - `ci.yml`)

Modern kurumsal mimarilerde CI botunun komut satırından doğrudan main dalına git push veya fast-forward yapması anti-pattern olarak kabul edilir. Araya giren hotfix veya squash PR'lar dalların çatallanmasına (diverging branches, exit code 128) yol açar ve kurumsal onay mekanizmalarını deler.

Model B Mimarisi & En Az Yetki Prensibi (Least Privilege):
GitHub Actions bir kod taşıyıcısı değil, ödünsüz bir Kalite Kapısıdır (Quality Gate). Geliştirici development dalına push attığında veya main dalına PR açtığında pipeline tetiklenir; Java 21, Testcontainers (PostgreSQL) ve Docker Multi-Stage build adımlarını doğrular. Repo izinleri güvenli contents: read seviyesinde tutulur.

.github/workflows/ci.yml 
name: Enterprise Spring Boot CI (Quality Gate)

on:
  push:
    branches: [ development, main ]
  pull_request:
    branches: [ development, main ]

permissions:
  contents: read

jobs:
  # =====================================================================
  # Quality Gate: Build, Unit & Testcontainers Integration Verification
  # =====================================================================
  build-and-verify:
    name: Build & Test (Java 21 + Testcontainers + Docker)
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4

      - name: Setup Java 21 LTS (Eclipse Temurin)
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: 'maven'

      - name: Run Maven Build & Integration Tests (PostgreSQL Testcontainers)
        run: |
          chmod +x ./mvnw
          ./mvnw clean verify -B

      - name: Verify Multi-Stage Dockerfile Build
        run: |
          docker build -t core-api-service:ci-test .

6 Conventional Commits Standartları

Depodaki tüm commit mesajları otomatik sürümleme (semantic release) ve okunabilirlik için <tip>(<kapsam>): <açıklama> formatında olmalıdır.

Tip Kullanım Amacı Örnek Commit Mesajı
feat Kullanıcıya veya sisteme yeni bir özellik/endpoint ekleme feat(user): add register user endpoint with jakarta validation
fix Bir hatayı (bug) düzeltme fix(auth): resolve JWT expiration timestamp timezone bug
test Birim veya Testcontainers entegrasyon testi ekleme/güncelleme test(order): add Testcontainers postgresql repository tests
ci GitHub Actions veya CI/CD scriptlerinde yapılan değişiklikler ci(workflow): enable maven dependency caching on ci.yml
chore İş mantığını etkilemeyen rutin işler (.gitignore, bağımlılık sürümü) chore(deps): bump spring-boot.version to 4.1.1 GA
refactor Davranışı değiştirmeden kod yapısını iyileştirme refactor(service): extract payment validation to strategy pattern

7 Geliştirici Günlük İş Akışı & Sürüm Yayınlama (Model B)

Model B mimarisinde geliştiricinin günlük akışı development dalında hız kazanırken, main dalı kontrollü sürüm onaylarıyla korunur:

Adım 1: Geliştirmeye Başlarken

# Daima en güncel development dalını çekin:
git checkout development
git pull origin development

Adım 2: Kodlama & Yerel Doğrulama

Kodunuzu geliştirin ve commit atmadan önce testlerin lokalde geçtiğini teyit edin:

# Testleri ve Testcontainers entegrasyonunu koşun:
./mvnw clean test

Adım 3: Commit & Push (development)

git add .
git commit -m "feat(product): implement pagination for product list query"
git push origin development

Adım 4: Otomatik CI Kalite Kapısı (GitHub Actions)

Push işleminden sonra GitHub Actions Kalite Kapısı otomatik devreye girer. Java 21, PostgreSQL Testcontainers ve Docker Multi-Stage build adımlarını doğrular. Testler yeşil (PASS) olmadan sonraki adıma geçilemez.

Adım 5: Sürüm Yayınlama & Production Dağıtımı (Release PR & Tag)

Sprint veya özellik paketi tamamlandığında GitHub arayüzünden development → main yönünde Release Pull Request açılır. Kalite kontrolleri ve kod inceleme (Code Review) onaylandıktan sonra PR Squash and merge veya Merge commit ile maine aktarılır ve sürüm etiketi (Git Tag) basılır: 

# main dalını güncelleyin ve resmi sürüm etiketini yayınlayın:
git checkout main
git pull origin main
git tag -a v1.0.0 -m "release: v1.0.0 core REST API enterprise release"
git push origin v1.0.0
Panoya kopyalandı!
