1 Şemanın Tek Kaynağı (Single Source of Truth)

Kurumsal mikroservis mimarilerinde Hibernate'in doğrudan veritabanı şemasını değiştirmesi (ddl-auto: update / create) kesinlikle yasaklanmış kritik bir anti-pattern'dir. Şemanın tek sahibi ve otoritesi Flyway'dir.

❌ Hibernate ddl-auto: update (Yasaklı Yaklaşım)

Hibernate tablo ve sütunları otomatik oluşturduğunda:

  • Sütun silinmelerini veya tip değişikliklerini asla yapamaz, yetersiz kalır.
  • İndeksleri kontrolsüzce veya verimsiz varsayılanlarla üretir.
  • Üretim (Production) ortamında veri kaybına ve şema sapmalarına (drift) neden olur.
  • Kim, ne zaman, hangi SQL'i çalıştırdı denetim izi (audit) tutulamaz.
✅ Flyway + ddl-auto: validate (Kurumsal Standart)

Şema sadece versiyonlu SQL dosyalarıyla yönetildiğinde:

  • Tüm şema değişiklikleri Git versiyon kontrolü altında incelenebilir (Review).
  • PostgreSQL 16 eklentileri (citext, pgcrypto) ve kısmi indeksler tam güçle kullanılır.
  • Hibernate yalnızca şemanın doğruluğunu onaylar (validate) ve güvenle ayağa kalkar.
  • Testcontainers ve CI/CD süreçleri sıfırdan üretimle %100 özdeş şema kurar.
📁 Flyway Dosya İsimlendirme ve Dizin Yapısı

Tüm migration script'leri src/main/resources/db/migration/ dizini altında yer almalıdır:

Önek / Tip Örnek Dosya Adı Açıklama & Çalışma Mantığı
V{Sürüm}__ V1__init_extensions_and_base_schema.sql Versiyonlu Migration: Yalnızca bir kez sırasıyla çalışır, checksum kontrolüyle mühürlenir. Çift alt tire (__) zorunludur.
V{Sürüm}__ V2__add_user_phone_number.sql Artımlı (Incremental) Değişiklik: Var olan şemaya yeni tablo, sütun veya indeks ekler.
R__ R__create_active_users_view.sql Tekrarlanabilir (Repeatable) Script: View, Stored Procedure veya Function nesneleri için kullanılır. Dosya içeriği değiştiğinde otomatik tekrar çalışır.

2 Kilitlenme Koruması (Lock-Safe DDL & Concurrency)

PostgreSQL'de DDL işlemleri (ALTER TABLE, indeksleme) tablo üzerinde ACCESS EXCLUSIVE kilit talep eder. Yoğun çalışan sistemlerde kilit zaman aşımı tanımlanmazsa, arkasından gelen tüm basit SELECT sorguları kuyrukta tıkanır ve tüm uygulama kilitlenir (Connection Starvation).

Kritik Kural (Her DDL Script'inin Başına Eklenmelidir):
Her V...sql dosyasının ilk satırlarında mutlaka statement_timeout ve lock_timeout parametreleri tanımlanmalıdır. Tablo 5 saniye içinde kilitlenemezse işlem derhal hata vermeli, kilit kuyruğunu tıkamamalıdır.

Standart DDL Kilit Zaman Aşımı Başlığı 
-- 1. Sorgu ve Kilit Zaman Aşımları (Lock Starvation & Hanging DDL Koruması)
SET statement_timeout = '60s';
SET lock_timeout = '5s';
💡 PostgreSQL 11+ Güvenli Sütun Ekleme (Lock-Safe Column Addition)

PostgreSQL 11'den itibaren DEFAULT değeri olan bir sütun eklendiğinde, PostgreSQL tüm tabloyu baştan yazmak zorunda kalmaz (sadece sistem kataloğunu günceller, O(1) maliyet). Bu sayede milyonlarca satırlık tablolara bile anında ve kilitlenme riski olmadan sütun eklenebilir: 

-- Milyonlarca satırlık tabloda dahi 1 milisaniye içinde tamamlanır (Metadata-only rewrite):
ALTER TABLE users ADD COLUMN is_verified BOOLEAN NOT NULL DEFAULT FALSE;

3 PostgreSQL 16+ Modern Tipler & citext Eklentisi

Modern PostgreSQL veri tipleri performansı maksimize eder, bellek israfını önler ve uygulama katmanındaki karmaşıklığı veritabanı seviyesinde doğal olarak çözer.

🔑 BIGINT IDENTITY

Eski SERIAL veya BIGSERIAL yerine modern SQL standartlarına uygun BIGINT GENERATED ALWAYS AS IDENTITY kullanılır. Otomatik sequence üretir ve manuel ID ezilmesini engeller.

🕒 TIMESTAMPTZ (UTC)

Asla TIMESTAMP WITHOUT TIME ZONE kullanılmaz! Zaman dilimi belirsizliğini sıfırlamak için daima TIMESTAMPTZ kullanılır ve uygulama UTC saat dilimine mühürlenir.

🔤 citext Eklentisi

E-posta ve kullanıcı adı alanlarında LOWER() fonksiyon indekslerine gerek kalmadan doğal büyük/küçük harf duyarsız (Case-Insensitive) arama sağlar.

🔍 citext Eklentisi Neden Hayat Kurtarır?

Klasik VARCHAR sütununda user@example.com ile User@Example.com farklı değerlerdir. Kullanıcı girişinde WHERE LOWER(email) = LOWER(?) yazmak hem sorguyu çirkinleştirir hem de standart B-Tree indeksini devre dışı bırakır.

citext ile Doğal Büyük/Küçük Harf Bağımsızlığı
-- 1. Eklentiyi ilk migration dosyasında bir kez yükleyin:
CREATE EXTENSION IF NOT EXISTS citext;

-- 2. Tablo tanımında veri tipini CITEXT olarak belirtin:
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email CITEXT NOT NULL,
    username CITEXT NOT NULL
);

-- Artık aşağıdaki iki sorgu da B-Tree indeksini %100 kullanarak aynı kaydı bulur:
-- SELECT * FROM users WHERE email = 'john.doe@company.com';
-- SELECT * FROM users WHERE email = 'John.Doe@Company.COM';

Java tarafında geliştirdiğimiz kurumsal BaseEntity.java sınıfı (Dual-ID, Optimistic Locking, Full Auditing, Soft Delete) veritabanı şemasında birebir aşağıdaki sütun yapısıyla karşılık bulmalıdır.

Long id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY İç Veritabanı ID: Foreign key bağlantıları ve clustered indeksleme için maksimum performans. Dış dünyaya kesinlikle açılmaz.

5 Soft Delete & Kısmi İndeksler (Partial Indexes)

Mantıksal silme (Soft Delete) uygulanan tablolarda klasik UNIQUE kısıtları ciddi bir mimari kriz yaratır. PostgreSQL'in Kısmi İndeks (Partial Index) özelliği bu sorunu kökünden çözer.

⚠️ Klasik UNIQUE Kısıtının Çöküş Senaryosu

Tabloya klasik ALTER TABLE users ADD CONSTRAINT uq_email UNIQUE (email); kuralı koydunuz:

  1. Kullanıcı hesabını sildi: deleted = true, email = 'ahmet@firma.com'.
  2. Aynı kullanıcı 3 ay sonra tekrar gelip ahmet@firma.com ile yeni hesap açmak istedi.
  3. HATA: Klasik UNIQUE kısıtı silinmiş eski kaydı da gördüğü için yeni kaydın eklenmesini engeller ve sistem çöker!
Çözüm: Sadece Aktif Kayıtları Kapsayan Kısmi İndeks (Partial Unique Index) 
-- Silinmiş kayıtları YOK SAYAN, yalnızca aktif kayıtlar için benzersizlik garantileyen indeks:
CREATE UNIQUE INDEX uq_users_email_active ON users (email) WHERE deleted = FALSE;
CREATE UNIQUE INDEX uq_users_username_active ON users (username) WHERE deleted = FALSE;

-- Sık sorgulanan filtrelerde de indeks boyutunu küçültmek ve performansı artırmak için:
CREATE INDEX idx_users_status_active ON users (status) WHERE deleted = FALSE;

Kısmi İndeksin Avantajları:
1. Silinmiş kayıtlar indekse dahil edilmediği için indeks boyutu (RAM tüketimi) dramatik olarak küçülür.
2. Kullanıcı sildiği e-posta ile sonradan tekrar kayıt olabilir.
3. Hibernate 6'nın @SQLRestriction("deleted = false") filtresiyle %100 uyumlu çalışır; Postgres sorgu optimizörü bu indeksi doğrudan seçer.

6 Spring Boot 4.1.1 application.yml & HikariCP

Flyway ve Hibernate JPA'nın uyum içinde çalışmasını sağlayan kurumsal konfigürasyon bloğu.

src/main/resources/application.yml 
spring:
  datasource:
    url: jdbc:postgresql://${POSTGRES_HOST:localhost}:${POSTGRES_PORT:5432}/${POSTGRES_DB:core_api_db}
    username: ${POSTGRES_USER:postgres}
    password: ${POSTGRES_PASSWORD:postgres}
    driver-class-name: org.postgresql.Driver
    hikari:
      maximum-pool-size: 10
      minimum-idle: 5
      idle-timeout: 300000
      connection-timeout: 20000
      max-lifetime: 1200000
      pool-name: EnterpriseHikariPool

  jpa:
    open-in-view: false # Anti-pattern ve sızıntıları önlemek için kesinlikle false!
    hibernate:
      ddl-auto: validate # Tabloları ASLA değiştirme; kontrol yalnızca Flyway'de!
    show-sql: true
    properties:
      hibernate:
        format_sql: true
        default_batch_fetch_size: 25 # N+1 sorgu problemini engeller
        default_schema: public
        jdbc.time_zone: UTC # Zaman damgalarını UTC standardına mühürler
        order_inserts: true
        order_updates: true

  flyway:
    enabled: true
    baseline-on-migrate: true
    locations: classpath:db/migration
    validate-on-migrate: true
    out-of-order: false # Sırasız migration çalıştırmayı engelle

7 Geliştirici Kriz Yönetimi & Sorun Giderme

Flyway ile çalışırken en sık karşılaşılan hatalar, pratik kurtarma yöntemleri ve hızlı komutlar.

🚨 Hata: Migration Checksum Mismatch

Daha önce çalışmış bir V1__...sql dosyasında typo veya sütun düzeltmesi yaptığınızda, Flyway güvenlik gereği uygulamanın açılmasını engeller: 

FlywayException: Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 1
-> Applied to database : -1827491823
-> Resolved locally    : 4920194821

🛠️ Çözüm (Lokal Geliştirme):

Lokal geliştirme ortamındaysanız, terminalden tek bir Maven komutuyla veritabanındaki kayıtlı checksum'ı dosyadaki yeni checksum ile eşitleyebilirsiniz:

Terminal
# Veritabanındaki checksum değerlerini dosyalardaki güncel değerlerle senkronize eder:
./mvnw flyway:repair

⚠️ Canlı Ortam Kuralı: Üretim (Production) ortamına çıkmış bir migration script'i ASLA değiştirilmez! Düzeltme için daima yeni bir V2__fix_column.sql dosyası eklenir.

🚨 Hata: Migration Failed (success = false)

SQL dosyanızda sözdizimi hatası veya eksik bir tablo varsa migration yarıda kalır. Flyway'in flyway_schema_history tablosunda ilgili sürüm success = false olarak kilitlenir.

  1. SQL dosyanızdaki hatayı bulun ve düzeltin.
  2. Terminalden ./mvnw flyway:repair çalıştırın (Başarısız olan kaydı geçmiş tablosundan temizler).
  3. Spring Boot uygulamasını tekrar başlatın (Flyway temizlenen adımı baştan kusursuz çalıştırır).

🔄 Lokal Docker PostgreSQL'i Sıfırdan Başlatma

Geliştirme esnasında veritabanını tamamen temizleyip tüm migration'ları sıfırdan test etmek istediğinizde:

Terminal (Docker Temizlik & Başlatma)
# 1. Mevcut PostgreSQL konteynerini ve volume verisini tamamen silin:
docker compose down -v

# 2. Temiz PostgreSQL konteynerini arka planda başlatın:
docker compose up -d

# 3. Uygulamayı çalıştırın (Flyway tüm script'leri V1'den itibaren sırayla koşar):
./mvnw spring-boot:run
🚀 Tam Örnek: V1__init_extensions_and_base_schema.sql

Tüm bu kuralları (kilit zaman aşımı, citext, identity, BaseEntity audit sütunları, soft-delete kısmi indeksleri) içeren üretime hazır şablon:

src/main/resources/db/migration/V1__init_extensions_and_base_schema.sql 
-- =====================================================================
-- Enterprise PostgreSQL 16+ & Flyway Baseline Migration
-- Lock-Safe, citext, Dual-ID & Soft-Delete Partial Index Blueprint
-- =====================================================================

-- 1. Kilitlenme Zaman Aşımları (Lock Starvation Koruması)
SET statement_timeout = '60s';
SET lock_timeout = '5s';

-- 2. Gerekli Eklentiler (Extensions)
CREATE EXTENSION IF NOT EXISTS citext;

-- 3. Örnek Tablo: Users (Dual-ID, citext, BaseEntity Audit & Soft Delete)
CREATE TABLE IF NOT EXISTS users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id UUID NOT NULL DEFAULT gen_random_uuid(),
    username CITEXT NOT NULL,
    email CITEXT NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'ACTIVE',
    
    -- Optimistic Locking
    version BIGINT NOT NULL DEFAULT 0,
    
    -- Audit Trail (Kim & Ne Zaman)
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by VARCHAR(100) NOT NULL DEFAULT 'SYSTEM',
    last_modified_by VARCHAR(100) NOT NULL DEFAULT 'SYSTEM',
    
    -- Soft Delete (Mantıksal Silme)
    deleted BOOLEAN NOT NULL DEFAULT FALSE,
    deleted_at TIMESTAMPTZ,
    deleted_by VARCHAR(100)
);

-- 4. Kısmi İndeksler (Partial Indexes - Soft Delete Uyumlu)
-- Sadece silinmemiş (aktif) kayıtlar için benzersizlik sağlar:
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_public_id ON users (public_id);
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_email_active ON users (email) WHERE deleted = FALSE;
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_username_active ON users (username) WHERE deleted = FALSE;

-- Sık filtrelenen durum alanı için kısmi indeks:
CREATE INDEX IF NOT EXISTS idx_users_status_active ON users (status) WHERE deleted = FALSE;
